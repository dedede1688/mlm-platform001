# 订单、退款与认证回归修复设计

**日期：** 2026-07-28

**级别：** P 级（订单、退款、资金与权限）

**状态：** 胡子老师已批准业务方向，待书面规格复核后实施

## 1. 背景与目标

本轮预览验收发现以下问题：

1. 后台可将已支付订单直接改为已取消，且无二次确认、无防重复提交。
2. 已登录用户进入商品详情后，可能在用户资料尚未加载完成时被“立即购买”误跳转到登录页。
3. 已通过退款申请可在未完成退款前被订单完成流程越过，最终形成“订单已完成、退款已通过但无法退款”的冲突状态。
4. 认证数据迁移到 `sessionStorage` 后，部分后台页面仍从 `localStorage` 读取角色，导致审批按钮被错误禁用。
5. 退款接口与前端使用不同错误字段，管理员只能看到“操作失败”，无法判断实际原因。

目标是恢复一条可解释、可审计、不可绕过的订单与退款状态链，同时统一前端认证来源，避免误登录跳转和误判无权限。

## 2. 已批准的业务规则

### 2.1 订单取消

- 只有 `pending`（待支付）订单允许取消。
- 后台与用户端取消必须共用 `OrderLifecycleService.cancelOrder()`。
- `paid`、`shipped`、`completed` 订单不得直接改为 `cancelled`。
- 已支付订单的资金回退必须走退款申请、审核、确认退款流程。
- 后台取消待支付订单必须显示二次确认。
- 提交期间必须禁用操作按钮，成功后立即关闭或刷新详情，禁止重复提交。

### 2.2 退款与订单完成

- 订单存在 `pending` 或 `approved` 退款申请时，不得确认收货、后台完成或自动完成。
- 新退款申请仍只允许从 `paid` 或 `shipped` 订单发起。
- 对历史遗留的“订单已完成且退款已批准”记录，允许管理员执行完整退款冲销。
- 允许退款的订单状态为 `paid`、`shipped`，以及仅在退款申请已经 `approved` 时的 `completed`。
- 退款完成必须把订单资金冲销与退款申请 `approved → completed` 放入同一数据库事务。
- 库存、积分、余额、升级积分、奖励、分红和资格统计继续使用现有退款冲销逻辑，不增加第二套实现。
- 通知和操作日志在核心事务成功后执行；任一外围副作用失败都不得把已经成功的退款伪装成失败，失败详情必须写入服务端错误日志供追查。

### 2.3 认证与权限

- 客户端 token 和用户缓存统一通过 `getAuthToken()`、`getAuthUser()`、`removeAuthToken()`、`removeAuthUser()` 访问。
- 禁止业务页面直接读取或删除 `localStorage` 中的 `token`、`user`。
- 本轮至少修复后台订单、退款、财务、商品、会员页面的角色读取。
- 同步修复购物车 401 和用户中心退出登录仍删除旧存储的问题。

### 2.4 商品购买登录判断

- 商品详情新增明确的用户资料加载状态。
- token 存在且用户资料仍在加载时，“立即购买”按钮不可触发登录跳转。
- 只有 `/api/users/me` 明确返回 `401` 时才清理认证并跳转登录。
- `403`、`404`、`500` 或网络错误必须保留登录状态并显示“用户信息加载失败，请重试”。
- 购买按钮在用户资料未就绪时显示加载状态或保持禁用。

## 3. 方案选择

### 3.1 已支付订单处理

**采用：取消仅限待支付，已支付统一走退款。**

未采用的方案：

- “保留已支付取消并自动退款”：会把取消与售后退款变成两套资金入口，审计和幂等风险更高。
- “只增加确认弹窗”：只能改善交互，无法解决资金、奖励和库存未回退的问题。

### 3.2 退款状态冲突

**采用：前置阻断订单完成，并为已批准的历史 completed 订单提供受控退款兼容。**

未采用的方案：

- “只允许 paid/shipped 退款”：无法处理当前及未来竞态产生的历史冲突记录。
- “所有 completed 订单都能直接退款”：绕过退款审核，不符合资金审批边界。

### 3.3 后台权限来源

**采用：页面统一调用现有认证工具读取缓存用户。**

未采用的方案：

- “把角色重新复制回 localStorage”：扩大 XSS 暴露窗口，并与认证治理目标冲突。
- “每页重新请求 `/api/auth/me`”：增加重复请求和页面闪烁；后续可再统一到全局认证上下文，本轮保持最小修复。

## 4. 组件与数据流

### 4.1 取消订单

```text
后台点击取消
  → ConfirmDialog
  → PATCH admin order status
  → 服务端确认当前状态仅为 pending
  → OrderLifecycleService.cancelOrder
  → 同一事务恢复库存/积分并更新 cancelled
  → 返回最新订单
  → 关闭确认框并刷新列表/详情
```

`paid → cancelled` 必须同时从前端操作表和后端状态转移表中删除，后端不能依赖前端隐藏按钮保障规则。

### 4.2 退款完成

```text
管理员确认退款
  → 校验退款申请为 approved
  → 校验订单为 paid/shipped，或 approved 退款对应的 completed
  → 单事务执行全部资金与业务冲销
  → 同事务更新订单 refunded + 退款申请 completed
  → 事务提交
  → 写操作日志与发送通知
  → 返回成功
```

订单完成入口在状态更新前查询是否存在 `pending/approved` 退款申请；存在则返回明确的 409 业务冲突。

### 4.3 前端认证

```text
页面挂载
  → getAuthToken / getAuthUser
  → 初始化角色权限
  → 异步刷新用户资料
     → 401：清理认证并跳登录
     → 其他失败：显示可重试错误，不跳登录
     → 成功：启用购买
```

## 5. 错误处理

- API 失败响应统一使用 `error` 字段。
- 前端展示顺序统一为 `data.error || data.message || 默认文案`。
- 可预期业务冲突返回 400 或 409，不返回 500：
  - `待支付订单才允许取消`
  - `订单存在进行中的退款申请，不能完成`
  - `退款状态不是已审批`
  - `当前订单状态不允许退款`
- 未知异常保留服务端日志中的原始错误，对客户端返回不包含敏感信息的明确操作文案。
- 核心退款事务提交后，通知或操作日志失败只记录服务端错误，不把接口响应改为退款失败。

## 6. 测试设计

### 6.1 服务与路由

- 待支付订单取消走生命周期服务并成功。
- 已支付订单后台取消被拒绝，且不会直接调用 `OrderService.updateOrder`。
- 同一取消请求重复提交时返回状态冲突，不重复恢复库存或积分。
- `pending/approved` 退款存在时，用户确认收货、后台完成、自动完成均被阻断。
- 已批准退款可对历史 `completed` 订单执行完整冲销。
- 未批准的 completed 订单不能退款。
- 退款资金冲销失败时，退款申请保持 `approved`。
- 退款申请更新失败时，前面的资金变更全部回滚。
- 通知失败时核心退款仍返回成功并保留可审计日志。

### 6.2 前端

- 后台五个权限页面不再读取 `localStorage.getItem('user')`。
- 超级管理员从 `sessionStorage` 恢复后，退款审核和提现审批按钮可用。
- 商品用户资料加载期间，立即购买不会跳登录。
- `/api/users/me` 返回 500 时显示重试错误且不清理认证。
- `/api/users/me` 返回 401 时清理认证并跳登录。
- 退款失败时优先展示 API 的 `error`。
- 订单取消按钮具有确认弹窗和提交中禁用状态。

### 6.3 回归验证

- 定向 Vitest 全绿。
- 全量 Vitest 全绿。
- `tsc --noEmit` 0 错误。
- `next build` 0 错误。
- 预览环境走通：
  1. 待支付订单后台取消。
  2. 已支付订单无直接取消入口。
  3. 已登录用户商品立即购买不误跳登录。
  4. 退款审核和财务审批按钮可点击。
  5. 历史 completed + approved 退款可完成冲销。

## 8. 非目标

- 本轮不修改数据库结构。
- 本轮不调整角色权限字典或菜单配置。
- 本轮不引入新的认证框架。
- 本轮不处理暗色模式、移动端重设计等 E 系列需求。
- 本轮不自动修复其他历史订单，历史数据审计另立任务。
