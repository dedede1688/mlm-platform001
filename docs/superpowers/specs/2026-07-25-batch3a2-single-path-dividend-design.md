# Batch 3A-2 分红唯一入账路径设计

> 状态：已获胡子老师批准，等待书面规格复核
> 日期：2026-07-25
> 等级：P 级（资金、权限与数据库结构）
> 前置保护：Batch 3A-1 周结资金写入保持暂停

## 1. 目标与唯一业务口径

胡子老师确认采用“即时入账制”：

- 订单付款成功后，分红立即进入接收人的 `earningsAvailable`。
- 同一订单、同一用户、同一分红池只允许发放一次。
- 每日任务不再重复生成分红。
- 每周任务不再执行分红资金入账。
- 后台原“分红结算”页面改为只读“分红记录”，不保留资金操作按钮。

本批必须同时解决重复发放、部分发放、支付成功后奖励漏发、退款重复扣回和历史状态错误。不得把“只禁用按钮”当作完成。

## 2. 已确认现状

### 2.1 当前存在三条相互冲突的路径

1. `RewardService.createDividendReward()` 在订单支付后按订单上级链生成 `Dividend`，并立即增加 `earningsAvailable`、写入 `dividend_reward` 流水。
2. `DividendService.snapshotDailyDividends()` 按当日全部已支付订单和全站等级池重新计算并生成 `settled=false` 的另一套记录。
3. `DividendService.settleWeeklyDividends()` 原计划再次增加 `earningsAvailable`，并写入 `daily_dividend` 流水和 `type=dividend` 奖励。

三条路径的参与人、金额计算、触发时点均不同，不能通过简单改一个状态字段解决。

### 2.2 生产只读基线

2026-07-25 审计结果：

- `dividends`：6 条，合计 ¥150。
- `dividend_reward` 资金流水：6 条，合计 ¥150。
- `daily_dividend` 周结流水：0 条。
- `type=dividend` 周结奖励：0 条。
- 其中 2 条、合计 ¥50 为 `settled=false`，但均已有即时入账流水。
- 未发现当前生产数据中相同 `user_id + order_id + user_level` 的重复记录。
- `dividends`、`rewards`、`balance_records` 均没有覆盖业务幂等键的唯一约束。

因此现有 ¥50 已经到账，只允许修正状态，禁止再次增加用户资金。

## 3. 总体架构

### 3.1 订单奖励状态机

订单增加奖励处理状态：

- `pending`：等待发放。
- `processing`：已被一个处理器抢占。
- `completed`：本订单全部奖励已发放。
- `failed`：本次发放失败，等待自动重试。

同时记录：

- `rewardAttempts`：已尝试次数。
- `rewardLastError`：最后一次失败原因，必须截断到安全长度，不记录密钥或完整请求。
- `rewardLastAttemptAt`：最后尝试时间。
- `rewardsCompletedAt`：全部奖励完成时间。

支付事务将新订单的奖励状态置为 `pending`。支付事务提交后立即调用奖励处理器。订单付款不能因为奖励失败而回滚；奖励失败必须留下可恢复状态。

### 3.2 单一奖励事务

一个订单的直推奖、品牌管理奖、分红、对应资金流水和用户可提现收益更新必须在同一个 Prisma 事务内完成。

处理顺序：

1. 通过条件更新把 `pending`、`failed` 或超时的 `processing` 抢占为 `processing`。
2. 在事务外读取只读业务配置并计算候选接收人。
3. 在一个奖励事务中创建奖励、分红、资金流水并更新用户收益。
4. 同一事务中把订单奖励状态改为 `completed`。
5. 任一资金步骤失败时，整个奖励事务回滚。
6. 回滚后在独立的非资金更新中把订单标记为 `failed`，记录错误和尝试次数。

不得吞掉奖励错误后把订单误标为完成。

### 3.3 自动补发

每日任务不再调用 `snapshotDailyDividends()`，改为重试符合以下条件的已支付订单：

- 状态为 `pending`；或
- 状态为 `failed` 且 `rewardAttempts < 5`；或
- 状态为 `processing` 且 `rewardLastAttemptAt` 早于当前时间 30 分钟。

每个订单最多自动尝试 5 次。超过上限后保留 `failed`，进入后台异常清单，不再自动处理。本批不提供“人工强制加钱”能力。

### 3.4 数据库最终防线

`Dividend` 增加明确的 `poolType`，取值限定为：

- `director`
- `manager`
- `supervisor`
- `president`
- `board`

数据库增加唯一约束：

```text
Dividend(orderId, userId, poolType)
```

奖励表必须按其真实业务身份建立对应唯一键，至少保证同一订单的同一用户不会重复获得同一种、同一层级奖励。空层级必须采用确定性的规范值或独立幂等键，不能依赖 SQL 中 `NULL` 的唯一性行为。

资金流水必须使用奖励或分红记录的真实 ID 作为 `sourceId`，确保流水能够追溯到唯一业务记录。

## 4. 分红生成规则

只保留当前订单支付链中的五个独立分红池：

1. 沿买家的上级链查找符合等级要求的用户。
2. 分别读取五个分红池比例与 `include_upstream` 配置。
3. 每个池独立计算池金额。
4. 同一池的合格用户平均分配该池金额。
5. 每个接收用户按 `orderId + userId + poolType` 生成一条分红。
6. 分红创建时即视为已到账；历史 `settled` 字段不再驱动资金行为。

本批不更改五个池的比例、等级资格或 `include_upstream` 业务含义。

## 5. 退款与审计保留

分红记录不得再在退款时删除。增加 `refundedAt` 表示该分红已扣回。

退款事务必须：

1. 只选择该订单尚未退款的有效奖励和分红。
2. 扣减 `earningsAvailable`。
3. 可提现收益不足部分增加到 `earningsVoided`，沿用现行资金规则。
4. 写入唯一、可追溯的负数退款流水。
5. 标记奖励状态和分红 `refundedAt`。
6. 在同一个事务中完成以上操作。

同一退款重复执行不得再次扣钱。退款后仍保留原始奖励、分红及正负流水，形成完整审计链。

## 6. 历史数据迁移

### 6.1 强制前置核对

迁移前必须运行只读核对，并同时满足：

- 分红记录为 6 条、合计 ¥150。
- 即时分红流水为 6 条、合计 ¥150。
- 周结流水为 0 条。
- 周结奖励为 0 条。
- 每条分红均能关联唯一即时入账流水。

任一条件不满足，迁移立即停止并重新审计，不允许“按预期数字强行继续”。

### 6.2 迁移规则

- 现有 6 条分红均标记为已到账；其中当前 2 条 ¥50 只改状态，不更新任何用户资金。
- 生产环境没有分红自定义配置，现有记录使用默认 `include_upstream=false`，可按 `userLevel` 回填 `poolType`。
- 不在迁移中硬编码生产记录 UUID。
- 上线前已经存在的订单统一视为历史已处理，避免新重试器突然补发历史奖励。
- 自动补发只处理新版本启用后的订单。

迁移前后必须再次核对用户资金字段、分红总额和分红流水总额，任何金额变化都视为失败。

## 7. 后台与定时任务

### 7.1 后台页面

原“分红结算”改名为“分红记录”，仅提供：

- 订单号、接收用户、分红池、金额、创建时间、退款状态。
- 按订单、用户、分红池和时间筛选。
- 奖励处理异常清单只读展示。

删除“执行日快照”和“执行周结”按钮。页面不得提供人工直接增加收益的能力。

### 7.2 接口与 Cron

- 移除后台手动快照和周结的资金能力。
- 每日 Cron 保留积分解锁、自动确认收货，并新增失败奖励重试。
- 每周 Cron 不再进行分红资金操作；确认无其他用途后删除对应计划和路由。
- Batch 3A-1 暂停闸门在新路径全部通过验证前必须保留。

## 8. 错误处理与并发

- 抢占奖励订单必须使用带状态和时间条件的原子 `updateMany`。
- 抢占失败表示已有其他处理器工作，当前调用正常退出，不重复计算资金。
- `processing` 超过 30 分钟才允许重新接管。
- 单次事务失败不得留下部分奖励、部分流水或部分收益。
- 唯一约束冲突必须被识别为幂等竞争，不得转换成第二次资金更新。
- 自动补发不得无限循环；第 5 次失败后停止。

## 9. 测试与验收

实施必须使用 TDD，至少覆盖：

1. 同一订单顺序调用两次，只产生一组奖励。
2. 两个任务并发处理同一订单，只允许一个成功。
3. 分红中途失败时，直推奖、品牌奖、分红、流水和收益全部回滚。
4. 支付成功但奖励失败时，订单保持已支付且奖励状态为 `failed`。
5. 每日任务可以补发失败订单，成功后变为 `completed`。
6. 第 5 次失败后停止自动补发。
7. 超时 `processing` 可以恢复，未超时不能被抢占。
8. 同一退款执行两次，只扣回一次。
9. 历史数据迁移前后用户资金数值不变。
10. 后台页面没有资金操作按钮。

实施计划必须拆分为可独立复审的批次：

1. 数据模型和安全迁移。
2. 单一奖励事务与幂等键。
3. 奖励状态机和自动补发。
4. 退款审计链重构。
